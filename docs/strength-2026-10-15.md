# Cache pressure and playing strength, October 15, 2026

The retained fix prevents the shared evaluation cache from consuming the Go
runtime memory budget and replacing useful search with garbage collection.
Existing cleanup now clears player caches above 75% of the runtime's memory
limit, as well as at the configured write limit. It releases owned persistent
ABDADA workers before GC so their references cannot retain the old evaluation
map and private transposition tables. No search heuristic, evaluation term,
clock budget, or configuration setting changed.

## Reproduced live failure

In mv1fVMW2, 29...Re4 spent 11.261 seconds, completed depth six, and scored
+238. Cold-hash Stockfish depth 22 instead prefers Nxe4 at -30 and scores
Re4 at -1355. Fixed depth-six/eight-worker replay reproduces Re4 and +238.

A controlled long-game replay applies all actual moves and logged Black
budgets, and ponders during observed White clock consumption. It uses the
production GOGC=400 and 2 GiB soft memory limit. It excludes sub-100ms book
windows and records core search without the outer mate-safety override or
additional Game.PlayTurn cleanup. Every budget/UCI pair, the final exact FEN,
and 28 prior Black turns are asserted. This establishes the cache mechanism;
it is not a complete reproduction of every client-side effect or an Elo test.

At the target, all searches receive 11.229 seconds and eight workers:

| Case | Move | Completed depth | Considered moves | GC CPU seconds |
|---|---|---:|---:|---:|
| Baseline cold FEN | Nxe4 | 7 | 2,156,468 | 0.890 |
| Baseline accumulated cache, exact history | Re4 | 6 | 916,634 | 65.638 |
| Baseline fresh cache, same exact history | Nxe4 | 7 | 2,157,039 | 1.021 |
| Candidate accumulated cache, exact history | Nxe4 | 7 | 2,239,200 | 2.495 |

The baseline starts the target with 18,350,617 cache writes and 2,709 MiB of
allocated heap, still below the 20-million-write cleanup threshold. GC object
scanning accounts for 71.24% of sampled CPU. Candidate cleanup holds the target
cache to 2,764,287 writes and 915 MiB before search. It considers 2.44 times as
many moves in the same budget. Two further target searches also choose Nxe4,
both completing depth eight. These repeats share the candidate replay state.
The largest phase-end heap sample changes from 2,730 to 1,723 MiB; this is
sampled allocation, not a hard peak-memory guarantee.

## Verification and deployment

The cache regression fails before the patch and passes afterward in 0.016
seconds. It covers memory-pressure eviction, releasing/rebuilding owned worker
contexts, forced clearing, and below-budget retention. Targeted cache,
quiescence, and parallel-root race checks pass in 16.806 seconds.

Two AI suite attempts pass every other test but fail the unchanged one-second
TestLazySMPFindsHangingKnight (90.685 and 91.524 seconds overall). That same
failure reproduces once in five runs on the unmodified deployed source; the
candidate passes five isolated runs. TestAIBestMovesSame is explicitly
skipped and existing in-test skips remain. No assertion was weakened. The
full AI suite is not claimed clean. Production build and git diff --check pass.
