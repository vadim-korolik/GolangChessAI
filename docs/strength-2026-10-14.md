## Completed-depth reproduction and runtime-cost hypothesis

A cold eight-worker replay limited to completed depth six reproduces exactly
Re4 and score +238 in 2.441 seconds, matching the live choice and score. This
removes the need to posit stale-cache corruption to explain the move at that
depth. The remaining discrepancy is useful depth completed within the clock:
the live search stopped at six after 11.261 seconds; cold 11.229-second
repeats finish seven or eight and avoid Re4.

Two debug blocks matching the preceding Black score sequence +655, +740,
+238 record 19,855,754 and 19,680,892 evaluation-cache writes. The configured
cache limit is 20,000,000, and the CLI runtime uses GOGC=400 with a 2 GiB soft
memory limit. `moveDebug.log` contains no game IDs or timestamps, so these
blocks cannot be attributed independently to one specific game. They are
strong leads for a controlled cache/GC profile, not proof of the cause.
Worker TTs reset per move; shared evaluation state persists across moves.
Exact diagnostic details and attribution limits are preserved in
`testdata/lichess_2026_10_14_re4_diagnostics.json`.

After reverting the rejected experiment, focused EP and unchanged
knight-defense checks pass in 3.777 seconds. The full original promotion
weakness remains open; no tactical exception or test weakening is retained.
The playing engine remains on the tested EP build, and 2400 Elo is unverified.

## Long-game cache pressure reproduced

An isolated replay applies every actual mv1fVMW2 move, searches earlier Black
positions with their exact logged budgets, and ponders during White's observed
clock consumption. It uses eight workers, GOGC=400, and the production 2 GiB
soft memory limit. Sub-100ms book windows are excluded. This is a controlled
core-search workload: it does not reproduce the outer mate-safety override or
additional Game.PlayTurn cleanup calls. Every budget/UCI pair, the final exact
FEN, and 28 prior Black turns are asserted.

| Target search | Cache writes before | Move | Depth | Considered | GC CPU seconds |
|---|---:|---|---:|---:|---:|
| Cold FEN | 0 | Nxe4 | 7 | 2,156,468 | 0.890 |
| Accumulated cache, exact history | 18,350,617 | Re4 | 6 | 916,634 | 65.638 |
| Fresh cache, same exact history | 0 | Nxe4 | 7 | 2,157,039 | 1.021 |

Each target receives 11.229 seconds. The warm case reproduces the live Re4
and +238 score; fresh cases score Nxe4 at +1. Heap allocation before the warm
search is 2,709 MiB and reaches 2,727 MiB, although the runtime soft target is
2,048 MiB. The cache remains below its 20-million-write clear threshold.
The warm profile attributes 71.24% cumulative sampled CPU to GC object scans.
It samples 77.18 CPU-seconds in 11.25 seconds, versus 34.05 CPU-seconds for
the fresh-history search. Equal GC cycle counts (20) mask the very different
cost of scanning the retained cache. This reproduces a concrete mechanism
for lost live search depth rather than inferring it from a cold FEN.

Baseline CPU profiles are preserved at
`/tmp/chess-oct15-cache-baseline-{cold-fen,warm-history,fresh-history}.pprof`.
The first heap dump is excluded: compiler liveness allowed the old player to
be collected before it was written. The candidate harness keeps the player
alive explicitly; in-search runtime counters and CPU profiles are unaffected.

The local fix extends existing move-boundary cache cleanup to act above
three quarters of Go's runtime memory limit. It retains the configured write
limit and adds no new setting. Cleanup also releases owned ABDADA worker
contexts before GC: those contexts otherwise retain the old shared evaluation
map and their private TTs after parent maps are replaced. A regression fails
on both old behaviors and passes after the fix; it also checks below-budget
retention and rebuilding workers against the new map.

Targeted cache, quiescence, and parallel-root race checks pass in 16.806
